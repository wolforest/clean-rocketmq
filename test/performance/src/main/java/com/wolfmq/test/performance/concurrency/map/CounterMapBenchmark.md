## 结论

1. **`HashMap<String, AtomicLong>` 全线胜出**，单线程快 1.2-1.4×,高并发下优势扩大到 **1.6-2.6×**。
2. **差距随并发线性放大**:t=1 差 ~1.3×,t=16 差 ~2×;size=100 的热点 key 上最夸张(265→552ns)。原因:`CHM.merge` 每次都对桶头做 CAS、冲突时自旋重试 + `Long::sum` 装箱分配，而 `AtomicLong` 的 `incrementAndGet` 是单个 CAS 且无装箱。
3. **map 尺寸影响很小**(100-2000 内两者都基本平稳)：竞争集中在少数热 key 上时(本测试随机 key,size=100 碰撞率高)CHM 退化更明显。
4. **代价**：AtomicLong 方案牺牲了并发安全结构——`HashMap` 本身非线程安全，前提是“key 集合固定不变”(无 resize、无 put/remove),这在你的 commitlog 场景(`shardingNumber` 固定后按 shardId 计数)恰好成立。

**对 CommitLog 计数器场景的启示**:固定 key 集合 + 高并发计数，`HashMap<String,AtomicLong>`(或按 shardId 的 `AtomicLong[]`)是更优选择;`CHM.merge` 适合"key 可能动态出现”的场景。
