L1：核心原语与微基准层（Micro-benchmark）

P0 立即落地

剥离 I/O 与网络，在纳秒/微秒级量化 CPU 热点、对象分配与锁竞争，消除 JIT/GC 干扰。

覆盖核心类
MessageEncoder/Decoder、OffsetCodec、EnqueueLock/DequeueLock/CommitLogReentrantLock、DefaultMappedFileQueue（Mmap vs TransientPool）、TimerWheel
工具与归口
JMH（test/performance），配合 -prof gc 与 -prof async 排查伪共享与内存拷贝。

L2：存储引擎组件层（Store 域内闭环）

P0 核心卖点验证

直接驱动 Store 领域层，量化存储极限，重点验证“CommitLog 分片 5x+ 吞吐”与后台派发追赶能力。

核心测试维度
① CommitLogManager 1/2/4/8 分片 × 线程数 × 单/多盘
② SYNC(GroupFlusher) vs ASYNC vs WriteCache
③ EnqueueService(enablePreAssignOffset) → DispatchManager → ConsumeQueue → DequeueService
工具与归口
重构现有 commitlog/benchmark 并沉淀至 test/performance，接入 HdrHistogram 输出 P99/P99.9。

L3：网络通信与协议接入层（RPC / gRPC / Registry）

P1 定位上移瓶颈

剥离磁盘 I/O 测出计算层与网络层天花板，确认 Broker 能否喂饱多分片存储。

核心测试维度
① Mock MQFacade 测 Broker gRPC 编解码与 producerThreadNum 上限
② rpc 模块 Netty 收发 QPS/RTT；registry 高并发路由拉取
③ 存算分离下 Embed vs Remote RPC 延迟差
工具与归口
test/performance 独立 Mock Store Broker 与 Netty RPC 压测程序。

L4：单节点端到端业务层（Broker + EmbedStore）

P0 对标 RMQ 5.x

通过标准 rocketmq-client-java 5.x 直连 Broker(:8081)，评估全业务场景真实吞吐与端到端延迟。

业务场景
① 普通消息：Sync/Async/Batch、热读 vs 积压冷读
② Pop 全闭环：Pop → Ack → Renew → 超时 Revive
③ 特性衰减：FIFO 顺序锁、Timer 延时误差、TCC 事务与回查
工具与归口
升级 test/e2e/benchmark（Open-loop 定速 + HdrHistogram），或接入 OpenMessaging Benchmark (OMB)。

L5：集群与高可用扩展层（HA 主从 / 存算分离集群）

评估主从复制对写吞吐/P99 的影响，以及多 Broker + 多 Store 水平扩容线性度。

测试重点

工具与归口

L6：长稳、极限与混沌压测层（Soak / Stress / Chaos）

03 · 现有压测资产审计与缺陷诊断

正式跑数前务必先修复
CommitLogManagerBenchmark.java 3 处失真
  • 多线程耗时被累加（L361/L392/L426）： totalTime.addAndGet(end - start) 将各线程耗时求和当分母，多线程吞吐被人为除以线程数；应改为外层墙钟时间。
  • 刷盘基准不对等（L495 vs L458）： 单 FileCommitLog 用 EmptyFlushHandler，而分片版走默认 SYNC 刷盘。
  • 未等落盘完成（L389）： runMultiThreadBenchmarkWithTopics 未调 future.get()。
InsertBenchmark.java 公式错误
  • 分子硬编码不匹配（L80/L105 & L121/L148）： 每线程写入 500,000 条，总条数应为 500,000L * cpuNumber，但打印吞吐时写死了 1000000 和 100000L * cpuNumber。
  • 无预热统计： 缺少 JIT Warmup 与多轮均值/方差收敛机制。
test/e2e/.../benchmark/ 功能局限 + 小 Bug
  • 场景单一： 只有同步单条 producer.send，缺异步、批量、Pop 消费、延时、事务基准。
  • 客户端过重： ProduceBenchmarkSuit 每线程独立 buildProducer 并建删 Topic，高并发下施压端先成瓶颈。
  • 延迟缺失 & 符号反写： Report.java 的 maxRT/averageRT 未埋点（缺 HdrHistogram）；BenchmarkSuit.java#L77 取 endTime 时 > 写反。
test/performance & test/stability 骨架就绪

两者均已在 test/pom.xml 声明并引入 store、broker、rocketmq-client-java，目前为空模块，建议直接作为 L1~L3（performance） 与 L6（stability） 的标准工程归口。

05 · 三层监控指标与火焰图剖析

测出数据 + 定界瓶颈

1. 业务与延迟指标

  • TPS（msg/s）、带宽（MB/s）、错误/超时率
  • HdrHistogram 统计 Send RT & Pub→Sub RT 的 P50 / P95 / P99 / P99.9 / Max
  • 内部水位：Dispatch Lag、队列深度、Pop InflightCounter
  • Open-loop 定速模式，避免 Coordinated Omission 延迟失真

2. JVM 与火焰图剖析

  • CPU 火焰图：Protobuf、MessageEncoder、CRC32、Netty 调度
  • Lock 火焰图：直观验证 CommitLogReentrantLock 分片前后与 EnqueueLock 争抢
  • Alloc & GC：排查 MessageBO/ByteBuffer 分配抖动与 DirectMemory

3. OS 与硬件层指标

  • 磁盘：wMB/s、rMB/s、w_await、%util
  • PageCache：/proc/meminfo 的 Dirty / Writeback（定位脏页毛刺）
  • CPU/网络：核心均衡、上下文切换、软中断与网卡丢包
压测现场诊断命令速查 
# 1. async-profiler 采集 CPU / Lock / Alloc 火焰图（60s）
./asprof -d 60 -e cpu   -f cpu-flame.html   <broker_pid>
./asprof -d 60 -e lock  -f lock-flame.html  <broker_pid>
./asprof -d 60 -e alloc -f alloc-flame.html <broker_pid>

# 2. Linux OS 磁盘 / 脏页 / 上下文切换实时观测
iostat -xz 1
watch -n 1 "grep -E 'Dirty|Writeback' /proc/meminfo"
pidstat -w -u -p <broker_pid> 1
sar -n DEV 1
